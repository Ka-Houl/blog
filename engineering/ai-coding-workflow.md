# AI 编程工作流：从 Vibe Coding 到 Agentic Engineering

## 四个阶段

| 阶段 | 人在做什么 | 典型问题 |
| --- | --- | --- |
| Vibe Coding | 用自然语言让 AI 直接产出可跑的东西 | 能跑，但没人说得清为什么 |
| Context 工程 | 主动组织 Rules、代码索引、约束与验收标准 | 上下文不足 → AI 反复跑偏 |
| SDD 规范驱动 | 先写清意图、规格、验收，再让 AI 实现 | 规格含糊 → 产出无法验证 |
| Agentic Engineering | 把单测、重构、CR、部署交给可控的 Agent 流程 | 流程失控 → 责任不清 |

> 演进方向不是「让 AI 写更多代码」，而是**把人的判断前移到规格与验收，把执行交给可控流程**。

## Context 工程：AI 表现的上限由上下文决定

| 输入 | 作用 |
| --- | --- |
| Rules / 约定文件 | 技术栈、目录约定、禁止事项、验证命令（如 `AGENTS.md` 类约定） |
| 代码索引与符号 | 让 AI 定位「改哪里」，而不是全仓盲扫 |
| 规格与验收标准 | 可验证的完成条件，替代「做得好一点」 |
| 最小复现与日志 | 排障时给真实错误，而不是描述感觉 |
| 约束边界 | 不许改哪些文件、不许提交密钥、必须跑哪些检查 |

::: tip 一条实操经验
把「验证命令」写进规则文件（例如 `npm run build`、某个探针脚本），
并要求「声称完成前必须实际运行」——能消灭大量「代码写完了但其实没跑通」的假完成。
:::

## SDD：Spec → Plan → Implement → Verify

```
① Spec      写清目标、边界、非目标、验收标准（可测）
② Plan      拆成可独立验证的小步骤，标注影响范围
③ Implement 每步小提交，AI 产出后人工读 diff
④ Verify    单测 / 构建 / 人工走查，不通过回到 ②
```

规范不是长文档，而是**可执行的判据**。
把「按钮要好看」换成「与设计稿字号/间距差值 ≤ 1px」，
AI 和人的验收才有同一把尺子。团队里常见的组合是
OpenSpec（规格）+ 规则文件 + 终端 Agent + 自动化检查。

## AI 参与的四类高价值任务

| 任务 | 为什么适合 | 人的把关点 |
| --- | --- | --- |
| 单测补全 | 目标明确、可自动验证 | 断言是否覆盖了真实边界，而不是凑覆盖率 |
| 重构 | 可依赖编译与测试兜底 | 行为是否等价、是否夹带无关改动 |
| Code Review | 能做一致性检查与清单核对 | 架构判断、业务语义仍由人负责 |
| 文档与迁移 | 模式化程度高 | 示例代码必须实际跑通 |

## 护栏：把「理解权」留在人这边

- **产出归我**：任何合入的代码，人能解释它为什么这样写、失败时会怎样。
- **过程看懂**：不接受「AI 改好了，别问」；diff 要逐块读，尤其是配置与权限相关改动。
- **坏账兜住**：AI 引入的技术债要登记、要有偿还计划，不能靠下一次生成掩盖。
- **最小权限**：Agent 能改的文件、能执行的命令要有边界；密钥与生产环境不开放给自动流程。
- **可回滚**：小提交 + 评测/测试闸门，让任何一次 AI 改动都能被单独 revert。

::: warning 最隐蔽的风险不是「写错代码」
而是**理解权外包**：长期只看结果不看过程，人会逐渐失去对系统的建模能力，
出问题既判断不了根因，也承担不了责任。工具越强，越需要自我纪律。
:::

## 团队提效怎么度量

别只统计「生成了多少行代码」。更有意义的指标：

| 指标 | 含义 |
| --- | --- |
| 需求交付周期 | 从规格确定到验收通过 |
| 首次通过率 | AI 产出一次通过测试/CR 的比例 |
| 返工率 / revert 率 | 生成代码被撤回的比例 |
| 缺陷逃逸率 | 上线后才发现的缺陷 |
| Review 耗时 | 是否真的降低了人的负担 |
