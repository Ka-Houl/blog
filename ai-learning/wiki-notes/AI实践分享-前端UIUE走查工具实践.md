## 0. 文档定位

本文是一篇**前端 UI/UE 自测走查工具的实践经验分享**，介绍了一个自研的 AI 辅助工具，用于在页面提交设计走查之前，帮助研发对照 MasterGo 设计稿和交互稿，自动检查 UI 还原偏差与交互实现遗漏，并输出可定位、可验证的问题报告。

---

## 1. 背景：解决什么问题

页面开发完成后，研发通常会验证功能能否跑通，但容易忽略：
- 按钮尺寸、文字字号、颜色、间距是否与设计稿一致；
- 取消、关闭、失败等分支状态是否处理正确；
- 空值、无信号、数据保留等边界场景是否遗漏；
- 自测依赖临时点击和个人记忆，难以追溯哪些已查、哪些未查。

**核心诉求**：作为研发自测辅助工具，在页面提交设计走查之前，对照稿件检查 UI 和交互实现，输出具体问题、定位依据及待补查项。

---

## 2. 两种自测维度

| 维度 | UI 自测 | UE 自测 |
|---|---|---|
| **核心问题** | 我实现的页面，样式是否符合设计稿？ | 我实现的操作与状态变化，是否符合交互稿？ |
| **典型问题** | 按钮偏小、字号颜色不对、间距不一致 | 取消后数据丢失、空值显示错误、禁用时缺少提示 |
| **检查依据** | MasterGo 设计稿 vs 实际运行页面 | MasterGo 交互稿 vs 对应代码 |
| **自测结果** | 元素差异、实际数值与页面位置 | 规则核查结果、实现依据 |

## 4. UI 自测：提前发现页面还原偏差

### 4.1 检查样式还原差异
- UI Skill 对照设计稿和实际渲染页面（**非截图比对**），检查文字、容器等元素。
- 覆盖属性：字号、颜色、位置、尺寸、背景色、边框、圆角等颜色和尺寸属性。
- 示例：设计要求文字 28px，实际 26px；容器宽度 112px，实际 171px；颜色差异等。

### 4.2 核查页面元素是否遗漏实现
- 列出设计稿中未在页面找到对应项的对象，供研发核对是否漏写、被错误隐藏或未满足显示条件。
- 例如：设计稿容器顶部有高亮线，实际页面未展示。
- **注意**：未找到对应项不直接等于遗漏实现，需结合页面状态确认。

### 4.3 定位问题并展示对比结果
- 自测结果提供具体元素的预期值、实际值及页面位置。
- 通过截图编号定位元素；未找到对应项的设计对象按所属层级展示。

## 5. UE（交互）自测：提前发现实现分支遗漏或错误

### 5.1 拆解交互规则至原子自测项
- 交互 Skill 整理稿件中的相关说明，拆成可逐项核查的检查项，避免只验证主路径。
- 示例规则：「电量显示为数字+%，如：45%，无信号仅内部为空的图标」
- 拆解为：
  - 电量区域的渲染
  - 电量存在有效信号或有效值
  - 电量无信号、无数据或为空
  - 电量从有效值变为空值

### 5.2 扫描代码，检查实际逻辑和交互稿描述是否一致
- 检查自动恢复时间是否一致；
- 检查是否有遗漏实现。

## 8. 当前限制

### 8.1 UI SKILL 限制

| 类别 | 例子及说明 | 备注 |
|---|---|---|
| **动态类** | CSS 动画：弹窗最终位置正确，但打开时闪烁；切换内容时抖动 | 引入动态类检测能力 SKILL |
| **复杂颜色类** | 复杂渐变 | 通过颜色/中间值可做一层判断；后续引入 VLM 检测流程 |
| **图片类** | 图标 / SVG / 背景图片 | 后续引入 VLM 检测流程 |
| **非 DOM 元素类** | Canvas、WebGL | 非 DOM 元素拿不到尺寸样式数据，后续单独适配开发 |
| **节点匹配类** | 设计树与 DOM 树结构差距较大时，匹配准确度依赖大模型能力 | 迭代节点匹配算法；后续开发 UI 实现工具，基于视觉稿实现并携带树结构数据，与 UI 走查工具联动 |

### 8.2 UE SKILL 限制
- UE 检查覆盖程度依赖大模型拆解是否完整。
- 如果某条要求没有被拆成检查项，后续逐项核查就可能漏掉。
- 例如：第三方组件中额外附带的动效等内容，目前通过滚动补充遗漏的 rule 作为 SKILL 读取上下文来解决，形成复利。

## 9. 核心实现原理

### 9.1 核心原则
> **确定的东西使用脚本来执行，不确定的交给 Agent 来裁决。**

### 9.2 整体执行流程
```
完整设计数据准备
├── UI：准备会话与目标页面 → 采集 DOM → 脚本匹配与候选 → Agent 逐条裁决 → 校验与报告
└── 交互：全文提取与原子规则台账 → 功能源码范围 + Agent 追踪实现与分支 → 结果、覆盖与执行摘要
```

- UI 有固定的结构比较引擎；
- 交互规则的理解和代码路径追踪主要由 Agent 完成。

### 9.3 完整设计数据准备
- 使用 **MasterGo MCP** 获取设计稿 DSL；
- 转换数据结构，供后续脚本进行节点匹配和属性差值计算。

## 10. UI 走查详细流程

### 10.1 登录态注入
- 通过前端系统管理平台提供的 MCP 服务获取对应前端系统的登录态 Cookie；
- Agent 启动无头浏览器时注入 Cookie，完成前端页面登录。

### 10.2 DOM 采集
- 采集整个页面的 DOM 节点树；
- 转换数据结构，供后续脚本进行节点匹配和属性差值计算。

### 10.3 设计稿节点与 DOM 节点匹配

#### 匹配思路
> 「先看你是什么、写了什么、站在哪里；再看你属于谁。」
- 先认出比较明显的文字，用文字认出整块区域，再用区域帮助认准内部元素；
- 遇到多人抢同一个对象就协调分配；
- 遇到拿不准的就把有限候选交给 AI 复核。

> 「是不是同一个元素」和「这个元素做得对不对」是两个不同的问题。即使位置偏了、尺寸错了，也应尽量认出它对应的设计按钮，然后再报告偏差，而不是因为长得不一样就认不出来。

#### 容器样式预处理
- 设计容器可能由独立矩形提供背景；
- 只允许符合条件的同边界视觉叶子层补充容器样式：相对起点及宽高误差在 1px 内，且不是任意文本或局部装饰；
- 示例：父节点是「live1」，实际容器背景色由子节点「容器 45767」提供，转换时会把「容器 45767」的背景色赋值给「live1」。

#### 节点匹配：先建立文本锚点，再定位容器
通 DOM 匹配主流程先处理文本、容器。所谓「先叶子、后容器」是指优先利用文本建立内容对应关系，并非严格按树深度逐层向上匹配。

**第一步：匹配文本节点，建立内容对应关系**
- 脚本为文本节点筛选设计候选；
- 计算文字、位置、尺寸、路径等分数；
- 结合父级范围内的局部分配及候选排序完成一对一匹配。

**第二步：从 DOM 容器内部的锚点寻找设计祖先**
- 处理 `div.card` 时，收集它内部已经匹配成功的文本；
- 沿对应设计文本的祖先链寻找结构容器；
- 需要判断候选容器是真实对应卡片，还是范围过大的页面根容器。

| 设计候选 | 内容支持 | 需要进一步判断的地方 |
|---|---|---|
| 保存按钮 | 只包含「保存」 | 不能代表整张卡片 |
| 任务卡片 | 包含三段对应文字 | 范围、尺寸和视觉特征是否与 DOM 卡片一致 |
| 页面根容器 | 也包含三段文字 | 可能只是范围过大的祖先，不能仅凭包含关系接受 |

- 脚本统计锚点支持数、文本相似度及祖先距离，并生成共同祖先约束；
- 不会直接把共同祖先当成最终答案。

**第三步：综合评分，建立容器匹配**
- 容器选择综合基础匹配分、锚点文本相似度、祖先距离。

### 10.4 Agent 裁决
- 第一轮节点匹配先选出一个匹配节点；
- 同时给出 K 个候选节点，交给 Agent 做裁决，给出最终匹配结果。

### 10.5 计算差异生成报告
- 根据 DOM 节点和设计稿节点的匹配关系，通过脚本计算各属性差异；
- 生成 HTML 报告。

## 11. UE 走查详细流程

```
完整 DSL → 全文清单 → 生成候选清单 → 生成正式空白台账 → 逐项追踪源码并填写证据 → 校验并生成报告
```

### 11.1 生成候选清单
- 按预设模式拆出可能的检查维度，例如：空值、点击、取消、数据保留、条件撤销。
- 示例：「飞行器编号无信号显示为 --」
  - 按空值预设模式「有值、空值、清空转换、字段存在」生成 4 个检查候选。
  - 1 个对象 × 4 个空值维度 = 4 个候选。

### 11.2 生成正式空白台账
- 记录每一条检查项的状态，确定完整检查计划。

### 11.3 逐项追踪源码并填写证据
- 沿事件、状态、共享组件和异步分支核对每项预期；
- 记录实际处理、源码片段及结论。

## 12. 后续建设思路

从四个方向持续建设：

### 12.1 流程上：构建自动化交付闭环
- 将检测与修复串联，形成「执行检测 → 修复问题 → 再次检测」的循环；
- 直至 Skill 检测无错误，推动走查从单次检查向闭环交付演进。

### 12.2 准确度上：融合视觉检测与经验积累
- 持续优化现有检测能力；
- 引入视觉语言模型（VLM）检测流程，补充复杂视觉场景识别能力；
- 建设检测经验库，沉淀典型问题与检查规则，持续提升准确度。

### 12.3 检测对象上：从 Web 拓展至小程序与 APP
- 逐步接入模拟器与真机走查能力；
- 支持小程序检测；
- 进一步探索 APP 走查，扩大适用范围。

### 12.4 工程化上：完善 Skill 与平台两种形态
- 持续优化 Skill 的易用性与复用能力；
- 拓展平台化形态，提供更便捷的任务配置、执行与结果查看体验。

## 13. 一句话总结

这是一个**基于 MasterGo DSL + 实际页面 DOM + AI Agent 裁决**的前端 UI/UE 自测走查工具：
- **UI 走查**：通过脚本将设计稿节点与 DOM 节点做属性级匹配和差值计算，发现样式还原偏差和遗漏元素；
- **UE 走查**：将交互稿拆解为原子检查项，由 Agent 追踪源码实现路径，发现分支遗漏和逻辑不一致；
- **目标**：在研发提交设计走查前，提前暴露 UI/UE 问题，输出可定位、可验证的问题报告，并逐步实现检测-修复-再检测的自动化闭环。
