# Multi-Agent：什么时候不该拆

> 多智能体是近两年最容易被滥用的架构。
> 判断力体现在：**能用一个 Agent + 几个工具解决的问题，就不要拆成一群 Agent。**

## 四种常见协作模式

| 模式 | 结构 | 适用 |
| --- | --- | --- |
| Supervisor / Worker | 主管接收任务、分派给专家、汇总结果 | 任务类型可清晰分类 |
| Planner / Executor | 规划者出步骤，执行者逐步落地 | 长任务、需要显式计划 |
| Researcher / Writer / Reviewer | 流水线 + 打回重写的循环 | 产出需要审校迭代 |
| Handoff / Swarm | 按对话状态把控制权交给另一个 Agent | 客服转接、多领域切换 |

共享的关键是 **同一份 State + 可追溯的 trace**：谁在什么时候写了哪个字段、
为什么路由到下一个节点，都要能回放，否则多 Agent 的排障会变成噩梦。

## 两个最常见的概念混淆

### 1. Node ≠ Agent

LangGraph 里的一个节点只是 `async (state) => 增量`。
一个确定性的「解析 JSON」节点、一个检索节点，都不是 Agent。
**只有当节点内部存在模型自主决策（选工具、定下一步）时，它才是 Agent。**
把 5 个确定性节点画成图，就宣称「我们做了 5 个智能体」，是最典型的包装话术。

### 2. Router ≠ Multi-Agent

一个分类节点把请求路由到不同 Prompt / 工具集，本质仍是**单 Agent 的条件分支**。
多智能体的标志是：多个具备独立决策能力、独立上下文/工具权限的执行主体之间发生协作。

## 五个判据：到底该不该拆

| # | 判据 | 若答案为「是」 |
| --- | --- | --- |
| 1 | 各角色是否需要**不同的工具集 / 权限**？ | 拆分有价值（权限隔离是真需求） |
| 2 | 各角色是否需要**独立、互不污染的上下文**？ | 拆分有价值 |
| 3 | 任务是否可**并行**且结果可合并？ | 拆分能降延迟 |
| 4 | 角色是否有**不同的生命周期 / 失败重试策略**？ | 拆分有价值 |
| 5 | 是否存在**互相审校 / 反思**的回环？ | 拆分有价值 |

若五条大部分是「否」，用单 Agent + 工具 + 条件边即可。**每多一个 Agent，
就多一份 System Prompt、多一轮模型调用、多一处出错点。**

::: warning Token 与延迟陷阱
Supervisor 模式每轮都要把各 Worker 的结果回传给主管再决策：
一次任务可能变成 5～10 次模型调用，成本与 P95 延迟成倍增长，
而且主管的上下文被塞满后决策质量反而下降。上线前务必用真实任务量测一遍平均步数。
:::

## 拆分原则：按业务边界，不按技术分层

- ✅ 按**职责与权限**拆：检索员（只读知识库）、审核员（只读 + 判定）、执行员（可写业务库）。
- ❌ 按技术层拆：「Prompt Agent」「SQL Agent」「日志 Agent」——这只是函数调用链。
- 每个 Agent 的工具集遵循最小权限；高风险写操作集中在少数节点，便于审批与审计。

## 让多 Agent 可控的四件事

1. **明确的终止条件**：`recursionLimit`、最大步数、最多重试次数、超时。
2. **共享 State 的 schema 化**：字段语义、reducer、谁可以写，先定义再写代码。
3. **trace 可回放**：记录 node / tool_call / token / 耗时 / 路由原因；用 LangSmith、LangFuse 之类平台。
4. **降级路径**：主管不可用时退回单 Agent；Worker 失败时转人工，而不是无限重试。

## DeepAgents 与 Deep Research

DeepAgents 一类框架把三件事标准化了：**显式 Planning（计划清单）、Sub-Agent 委派、上下文管理**
（大结果放文件系统/外部存储，窗口里只留引用）。典型应用是 Deep Research：
拆解问题 → 并行检索 → 归纳 → 审校 → 生成报告。
它适合长耗时、可中断、需要回溯的任务，不适合高并发的短问答。
